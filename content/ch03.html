3.1 Модель памяти

Физически память устроена сложно, а методы управления ею отличаются в разных архитектурах и ОС. Модель памяти — удобная абстракция, которая почти всегда позволяет писать код, не думая о низкоуровневых деталях.

Мы пишем код по правилам модели памяти, а реализация конкретных инструкций — на совести компилятора.

3.2 Модель памяти C++

Будем считать так:

  • Память — последовательность пронумерованных ячеек, которые называются байтами.
  • Номер ячейки — адрес.
  • Байт — минимальная адресуемая единица памяти.
  • Стандарт гарантирует: размер байта в точности равен размеру char.
  • Все ячейки равноправны, кроме нулевой: туда ничего нельзя записать и оттуда ничего нельзя прочитать.
  • Последовательность ячеек может интерпретироваться по-разному в зависимости от типа, который мы в ней «видим».

Представь длинную улицу из домов-байтов с номерами. int занимает 4 соседних дома, а его адрес — номер первого из них.

Хватило бы одного бита, но:

  • процессоры работают с байтами как с минимальной адресуемой единицей; доступ к отдельному биту — лишние операции (прочитать байт, сдвинуть, замаскировать);
  • компиляторы выравнивают данные на границы, кратные размеру машинного слова; 1 байт — минимальное выравнивание;
  • работа с целыми байтами и словами просто быстрее: железо под это оптимизировано.

Выравнивание в действии

На 64-битном Linux/macOS результат будет 16 и 24. Это и есть выравнивание. (На 64-битной Windows long — 4 байта, поэтому числа будут другие.)

Процессору удобно читать данные по адресам, кратным степени двойки:

  • int — по адресу, кратному 4;
  • long, double — кратному 8;
  • SIMD-типы — 16, 32 или даже 64.

Чтобы соблюсти правила, компилятор вставляет между полями «дырки» — padding. В A1 поля идут от мелкого к крупному, padding'а почти нет. В A2 после char сразу long, и компилятору приходится вставить 7 байт пустоты, чтобы long начался с адреса, кратного 8. А в конце ещё 4 байта, чтобы в массиве таких структур следующий элемент тоже был выровнен.

Поиграй с полями: двигай их стрелками и смотри, как меняется размер. Модель — 64-битный Linux/macOS.

Память читается блоками, чаще всего по 8 байт (64 бита). Пусть int лежит по адресу 62 (для простоты в десятичной). Его байты попадают в два блока: первый — в 56–63, последний — в 64–71. Чтобы прочитать такой int, процессор должен загрузить два блока, вырезать 4 нужных байта и собрать их. Медленно и бессмысленно, если можно положить данные по «ровному» адресу.

Поэтому: адрес переменной типа T должен делиться на alignof(T) — операцию, которая возвращает требуемое выравнивание типа в байтах.

#pragma pack живёт в коде сетевых протоколов и форматов файлов, где структура должна лечь на байты «из провода» один в один (заголовки BMP, пакеты игровых серверов). А сортировка полей по убыванию выравнивания — обычный приём оптимизации в игровых движках и HFT: миллион объектов по 16 байт вместо 24 — это лишние 8 МБ мимо кэша процессора.

64-битный Linux. Чему равен sizeof структуры struct S { char a; double d; char b; };?
a — байт 0, потом 7 байт padding до кратного 8, d — байты 8–15, b — байт 16, и хвостовой padding до кратного 8 → 24. Переставь double первым — будет 16. Проверь в виджете выше.

Глобальные переменные существуют всё время работы программы, но использовать их можно только после объявления! Чтобы использовать переменную, определённую ниже, её объявляют внутри функции с ключевым словом extern — «определена где-то в другом месте»:

Кажутся удобными, но на практике:

  1. Скрытые зависимости: любая функция может изменить глобальную переменную, появляются неявные связи.
  2. Сложность отладки: при ошибке трудно понять, кто изменил глобальное состояние.
  3. Проблемы с тестированием: тесты зависят от глобального состояния, их нельзя запускать параллельно или в произвольном порядке.
  4. Неопределённый порядок инициализации глобальных переменных в разных файлах.
  5. Занимают память всю программу, даже когда уже не нужны.
  6. Конфликты имён, особенно с библиотеками.

Если можно обойтись без глобальной переменной — обходись. Лучше явно передавать данные через параметры или прятать в объекты.

Инициализация переменных

Последние 4 строки так или иначе записывают значение в память переменной. Изменить значение потом можно присваиванием:

Инициализация через = — это не присваивание. int b = 1; создаёт объект сразу со значением; присваивание меняет значение уже существующего объекта. Для int разница незаметна, для классов (конструкторы!) — огромная.

Чтение неинициализированной переменной — UB. Пользоваться ей можно только после записи конкретного значения.

Бонус {}: запрещает сужающие преобразования. int k = 3.7; молча даст 3, а int k{3.7}; — ошибку компиляции. Поэтому многие кодстайлы советуют фигурные скобки.

Квалификатор volatile

volatile означает, что операции с переменной нельзя оптимизировать (удалять, переставлять с другими и т.п.). Полезно, когда переменная меняется «в обход» программы: регистр устройства, память, которую меняет другое железо.

Пример из конспекта, показывающий, как «поменять» константу. Это UB, и результат зависит от компилятора и расположения переменных.

  1. Создаётся константа x = 0 с volatile.
  2. Выводятся её значение и адрес.
  3. Создаётся обычная b = 10.
  4. ptr указывает на адрес «b + 1 int». Это UB, но часто он попадает ровно в x.
  5. По этому адресу пишется 100.
  6. Снова выводятся x и значение по указателю.

С volatile компилятор каждый раз читает x из памяти, и подмена «видна». Без volatile он вправе подставить вместо x константу 0 или закешировать в регистре, и изменения ты не заметишь, хотя память поменялась.

Код обращается к памяти за пределами b, может записать в случайное место стека, сломать другие переменные или служебные структуры. Не делай так в реальных программах!

  • const — обещание компилятору, что ты не будешь менять значение;
  • volatile — предупреждение, что значение может измениться извне;
  • volatile const — «я менять не буду, но кто-то другой может».

Запусти пример с -O0 и с -O2 в песочнице: раскладка стека зависит от компилятора и флагов, так что «трюк» может сработать в одном случае и не сработать в другом. В этом и суть UB.

volatile const — не только экзаменационный фокус. В прошивках микроконтроллеров так описывают регистры «только для чтения», значение которых меняет железо: например, регистр статуса UART. Программа не пишет туда, но каждый раз обязана читать заново.

Результат работы выражения проявляется в 1) возвращаемом значении и 2) побочных эффектах (side effects). Каждое выражение характеризуется типом и категорией значения. Категория отвечает на вопрос: материален ли результат, существует ли он в виде объекта в памяти.

Категории значений: lvalue и rvalue

Материальная категория — lvalue, нематериальная — prvalue (частный случай rvalue). lvalue соответствует месту в памяти, поэтому (за некоторыми исключениями) может стоять слева от присваивания. Теперь ошибка lvalue required as left operand of assignment понятна: 5 и x * y — не объекты в памяти, присвоить в них нечего.

Быстрый тест: можно ли взять адрес выражения через &? &x — да, значит lvalue. &(x + 1) или &5 — нет, значит rvalue.

Отметь lvalue-выражения (int x, y;).
  1. x
  2. x + y
  3. x = y
  4. x++
  5. ++x
  6. 42
x — переменная. x = y и ++x возвращают саму переменную x. А x++ возвращает старое значение — временную копию, это rvalue. x + y и 42 — тоже rvalue.

Операция sizeof

sizeof — унарная операция, возвращает размер в байтах.

  • Применённая к типу — сколько байт занимают объекты этого типа: sizeof(char) == 1 всегда, sizeof(int) == 4 вероятно (почему «вероятно» — см. главу 2).
  • Применённая к выражению — размер типа результата.

sizeof не вычисляет выражение, а только анализирует его тип на этапе компиляции.
