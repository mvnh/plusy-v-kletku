13.3 Арифметика указателей

Указатели — адреса. При выводе они выглядят как шестнадцатеричные числа, но целыми числами их считать нельзя. Арифметика к ним применима, только своя:

  • Указатели одного типа можно вычитать. Результат — сколько элементов типа T помещается в промежутке: (разница в байтах) / sizeof(T).
  • К указателю можно прибавлять целое. Результат — указатель, сдвинутый на n шагов размера sizeof(T).
  • Остальные арифметические операции недопустимы.

Стандарт ничего не обещает о взаимном расположении отдельных переменных: компилятор может положить их в любом порядке, с промежутками или вообще держать в регистрах. Более того, вычитание указателей на разные объекты (не элементы одного массива) — формально UB.

Чтобы p + 1 указывал на следующий объект типа T, а не на середину текущего. Если int занимает 4 байта, следующий int начинается через 4 байта. Указатель «знает» размер своего типа — для того в нём и хранится тип.

Разность указателей на отдельные переменные с точки зрения стандарта не даёт разумного результата, а разыменование указателей, «уехавших» с объекта, — UB. По-настоящему арифметика указателей нужна для массивов (глава 16).

13.6 Нулевой указатель

Чтение неинициализированной переменной — UB. С указателями так же: использование неинициализированного указателя (разыменование и даже просто чтение значения) — UB.

Указателю нельзя присвоить произвольное число (единственное исключение — 0):

Чтобы задать «пустое» значение и отличать корректный указатель от некорректного, есть нулевой указатель. Любому указателю можно присвоить 0 (или NULL из C), это интерпретируется как нулевой адрес.

По стандарту по нулевому адресу не может находиться никакой объект, поэтому разыменование нулевого указателя — UB.

Возникает асимметрия: целые числа присваивать нельзя, а 0 внезапно можно. Это особенно опасно при перегрузке функций.

Правильный способ в современном C++ — литерал nullptr. Это значение специального типа std::nullptr_t, который неявно приводится к нулевому указателю любого типа, но не приводится к целым.

Потому что 0 и NULL — это целые. Если есть перегрузки f(int) и f(int*), то f(0) и даже f(NULL) вызовут f(int) (или будет неоднозначность), хотя имелся в виду указатель. nullptr имеет свой тип и однозначно выберет f(int*). Запусти:

13.8 Висячий указатель

Висячий указатель (dangling pointer) указывает на объект, время жизни которого уже закончилось: локальная переменная вышла из области видимости, или динамическая память была освобождена.

Чтение или запись по висячему указателю — UB!

Не допускай провисания указателей! Обнуляй указатели после освобождения памяти или выхода объекта из области видимости.

Компилятор предупредит (address of stack memory associated with local variable 'x' returned), но скомпилирует.

13.9 Сравнение указателей

Операции == и != можно применять к любым указателям одного типа (или после преобразований):

  • они проверяют, указывают ли два указателя на один объект;
  • работают с любыми указателями, включая нулевые;
  • не зависят от того, лежат ли объекты в одном массиве.

Операции отношения <, >, <=, >=:

Имеют определённое поведение только если:

  1. указатели указывают на элементы одного массива;
  2. указатели указывают на нестатические члены одного объекта;
  3. оба — указатели на один и тот же объект или функцию.

В остальных случаях результат не определён и может отличаться на разных платформах и даже запусках.

Указатель на элемент «за последним» (&arr[5] для массива из 5) брать можно, а разыменовывать — нельзя. На этом соглашении построены все интервалы [begin, end) в стандартной библиотеке.

Сравнение с nullptr через == и != всегда корректно: ptr == nullptr — указатель нулевой, ptr != nullptr — не нулевой. А <, >, <=, >= с nullptr стандартом не определены. Используй только == и !=.

Особенности сравнения разных типов указателей:

  1. указатели разных типов можно сравнивать на равенство после приведения;
  2. void* можно сравнивать с любыми указателями;
  3. указатели на разные типы нельзя сравнивать через <, >, <=, >= без явного приведения.

13.10 Динамическое выделение памяти

До сих пор переменные жили в глобальной области и на стеке. У них ограничения:

  1. Строго фиксированное время жизни: глобальные — до конца программы, локальные — до конца блока.
  2. Эти области обычно ограничены несколькими мегабайтами, а реальным программам часто нужно гораздо больше.

new

Выражения new T / new T(...) / new T{...} создают объект типа T в динамической области (куче) и возвращают указатель на него.

Объекты в динамической области живут с момента вызова new и до вызова delete. Поэтому можно создать объект внутри блока и пользоваться им снаружи.

Но так память постепенно засоряется: пока её никто не освобождает.

delete

Память в куче можно (и нужно) освобождать, как только она стала не нужна. delete <указатель> удаляет объект и освобождает память для повторного использования.

Замечание 1. Удалять можно только память, выделенную через new. В остальных случаях delete — UB (в том числе delete адреса переменной на стеке и повторный delete).

Замечание 2. Удаление нулевого указателя — корректная операция, ничего не делает.

Утечка памяти

При некорректной работе с указателями или несвоевременном освобождении возникает утечка памяти — неконтролируемый рост неиспользуемой памяти.

Аккуратное использование new и своевременный delete — залог победы над утечками. А в главе 15 узнаем, как сделать так, чтобы delete вообще не нужно было писать руками.

Утечки — не теоретическая проблема. Сервер, который теряет 100 байт на каждый запрос, при 10 000 запросов в секунду «съест» 3,5 ГБ за час и будет убит системой. Для поиска таких багов есть инструменты: AddressSanitizer (-fsanitize=address), Valgrind, Instruments на маке. В Chromium для управления памятью придумали целую систему умных указателей, потому что ~70% серьёзных уязвимостей там — ошибки работы с памятью.

Какие фрагменты приводят к UB?
  1. int* p = new int(5); delete p; delete p;
  2. int* p = nullptr; delete p;
  3. int x = 3; int* p = &x; delete p;
  4. int* p = new int(5); delete p; std::cout << *p;
A — двойное освобождение. C — удаление того, что не выделяли через new. D — чтение через висячий указатель. B — корректно: удалять nullptr можно.
